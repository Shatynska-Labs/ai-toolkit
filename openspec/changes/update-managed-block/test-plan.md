# Test plan: update-managed-block

Written by `ai-toolkit:change-test-writer` before implementation. The OpenSpec schema does not know about this file, so `openspec instructions apply` will not list it. Read it on purpose before implementing.

Run one case with `bash tests/run.sh <case>`, or several with `bash tests/run.sh <case> <case> ...`. Each case is `tests/cases/<case>.sh`.

## Situation and baseline

- **Situation.** The update tool does not exist yet (first situation). Every `project-update-*` case runs the tool. The four `project-init-*` cases run the existing `scripts/project-init` against wording the change revises. The static half of `project-update-older-bash` is the only third-situation check: it reads the source without running it. Its fixture-driven discriminator (a clean fixture plus one specimen per construct) ran in this pass and passed, because it runs before the target-absent guard.
- **Baseline (full suite, before any case was written).** `bash tests/run.sh` at commit 103c86f on bash 5.2.21, ShellCheck present, uid 1000. Result: **307 passed, 0 failed**.
- **After this pass.** The 50 new cases were run on their own:
  - 46 `project-update-*` cases fail in **state 2 (target absent)**. Each one stops at `require_update` with `target absent — .../scripts/project-update does not exist yet`. Their assertions have not executed, so whether they are sound is still unverified.
  - The 4 `project-init-*` cases fail in **state 1**. They run and fail on a specified assertion, because the `conventions file:` / `backlog:` line still says "out of scope" and neither names `scripts/project-update` nor says `ahead` or `malformed`.
  - The full suite was run again afterwards. The 307 existing cases still pass, and the only failures are these 50 new cases (see the report).
- **Fixture helpers checked by hand.** The preamble helpers were checked outside the suite against a specimen project before the cases ran: `seed_all` wrote a block for every record, `hash_ok` accepted each one, and `edit_inside` made `hash_ok` reject the edited block. That check is not part of the suite. Inside the suite, the cases that read project-init's real output (`project-update-current-untouched`, `project-update-replacement-equals-project-init`) cross-check that the helpers' hashing matches the tool's.
- **Not executed here.** The run half of `project-update-older-bash` needs a bash 3.2 (`$BASH32`, `bash3.2`, `bash-3.2`, or a `/bin/bash` that reports 3.2). None is installed on this host, so that half exits 0 without running. It is recorded here as not run, not as passing.
- **Cases that cannot run as root.** `project-update-unusable-target-blocks`, `project-update-write-failure-reports-written` and `project-update-legacy-readme-write-failure` cause failure through file permissions. Running as root, they fail on purpose instead of passing without testing anything.

## Derived assertions

These are recorded so the implementer can tell them apart from the spec. The spec states that a record's line *begins with the record's name* and *states* a classification. It does not fix the wording. The tokens below come from design.md decision 7 or were chosen in this pass, and each is matched loosely (case-insensitive, a substring, on the record's line):

- A record's line is the first report line matching `^<name>:` (`rline`). The colon comes from design.md decision 7. Used by every case that calls `expect_line` or `refuse_line`.
- The state words matched on that line are `current`, `replaced`, `edited`, `ahead`, `malformed`, `absent`, `not` + `write` (not writable), `project-init`, `backlog-migrate`, `v12`, `not checked`, `git diff`, and `README`. The versions are matched as substrings.
- Outcomes are matched as the whole word `SUCCESS` / `ERROR` / `BLOCKED` anywhere in the report, together with the exit code. The `Outcome:` prefix is not required.
- `Attention:` is matched as an exact whole line, because the requirement fixes it: `Attention: ` followed by names, comma-separated, in manifest order.
- `project-update-help`: each outcome and its code appear on one line. This follows `project-init`'s `--help` layout.
- `project-update-edited-diff`: the changed line appears on an indented report line that begins `-` or `+` after the indentation.
- `project-update-legacy-readme-backlog-converted`: "exactly `@AGENTS.md`" allows a single trailing newline.
- `project-update-legacy-readme-beside-own-claude`: the line to add is a report line that names `docs/backlog/CLAUDE.md` and `@AGENTS.md`.
- `project-update-legacy-root-link-outside-blocks`: the link counts as named when `AGENTS.md` appears on a report line other than `Target:`.
- `project-update-presence-agrees-with-project-init`: project-init's "present" is a `backlog:` line saying `already present`, and project-update's "absent" is a `backlog:` line containing the whole word `absent`. Two control forms are added: no marker at all, and `<!-- ai-toolkit:backlog-old 1.0.0 -->`, where the prefix without its trailing space would match.
- `project-init-*` cases: the superseded "out of scope" wording must be gone from the revised lines. That is the replaced assertion, stated as a negative.
- Exit 0 is asserted where a scenario says SUCCESS or "does not fail" without giving the code. The code comes from the outcome requirement.

**Deliberately untested (requirement text with no scenario):**
- The requirement that no option overwrites an edited block. An absent flag cannot be shown by a finite run.
- That an `absent` record creates no `.gitignore`, repository or specification tooling. Only "creates no `docs/workstreams/`" is asserted.
- On `ERROR`, the restorable / created / replaced marking of each named file. Only the naming is asserted, and only where the order of writes makes it non-vacuous (see Q3).
- `rules/README.md`, `AGENTS.md` and `skills/project-init/SKILL.md` wording (task 2.3). These are prose with no scenario in this change.

## Unresolved project questions

- **Q1. Report wording.** The spec fixes only "a line beginning with the record's name", `Attention: ...`, and the outcome words. Assumption taken: design.md decision 7's report form (`<name>: ...`), with the state words listed under *Derived assertions* matched loosely. Depends on it: every case that calls `expect_line` or `refuse_line`, `project-update-presence-agrees-with-project-init`, `project-update-edited-diff`, `project-update-legacy-root-link-outside-blocks`, and `project-update-legacy-readme-beside-own-claude`. If the implementation words a line differently but still meets the spec, these tokens are derived and may be reconsidered as derived assertions. They are not specified ones.
- **Q2. Bash stack skill.** The `bash` skill was loaded and applied: ShellCheck is clean on all 50 cases, and every `disable` names its code and gives a reason. The project records no convention for a bash 3.2 test host. Assumption: the same "run half where a bash 3.2 is found" approach as `backlog-migrate-older-bash.sh`. Depends on it: `project-update-older-bash`.
- **Q3. Write order.** The spec does not say that blocks are written in manifest order. Assumption: they are (design.md decision 7 reports in manifest order, and "the first" / "the second" in the failed-write scenario reads that way). Depends on it: `project-update-write-failure-reports-written` and `project-update-legacy-readme-write-failure`. The second asserts that the root `AGENTS.md` is named only where the workflow record comes before `backlog` in `rules/manifest` *and* the root block was in fact written.
- **Q4. How a failed write is caused.** No mechanism the suite controls fails a write midway except permissions. Assumption: a directory with mode 555 makes the tool's temporary-file write fail (design.md decision 3 writes the temporary file in the target's directory). The tool is also assumed not to pre-check per-directory write permission and report BLOCKED. Its preconditions as listed are the target, the manifest and fragments, the hash command and the git checks, and the `not writable` state covers links and wrong types, not permissions. Depends on it: `project-update-write-failure-reports-written` and `project-update-legacy-readme-write-failure`. If the implementation pre-checks permissions, these two would see BLOCKED (state 1 against the ERROR assertion). That would then need a decision between the spec ("a write attempted and failed") and the mechanism.
- **Q5. The target in the unusable-target cases.** The tool is assumed to accept a path argument that names a missing directory or a file, and to report BLOCKED with exit 2, not fail on argument parsing. Depends on it: `project-update-unusable-target-blocks`.
- **Q6. Environment variable for self-location.** The spec says "an environment variable names another copy" without naming one. Assumption: `AI_TOOLKIT_ROOT` (project-init's precedent) and `TOOLKIT_ROOT`. Depends on it: `project-update-self-location`.
